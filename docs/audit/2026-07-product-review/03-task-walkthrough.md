## 主任务 1：个人复盘闭环

| 目标与预期     | 实际入口与上下文                                             | 产品给出的内容                                               | 证据、返回与下一步                                           |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 找到比赛       | 资料库 → `加载 7 图示例`                                     | 比赛列表、地图、标签和 2D 回放可用性                         | 导入/找到比赛清楚。                                          |
| 标记“这是我”   | 我的主页候选卡 `FalleN` → 选手档案 → `设为关注选手（这是我）` | 档案页给出 RR、ADR、K/D、弱项                                | 候选卡并不直接完成标记，而是一次跳转；标记成功后主页切换为 FalleN。 |
| 发现问题       | 我的主页 → `本周该练什么`                                    | 主动列出 weak multi-kill、weak K/D、weak ADR；并给出“长枪局首死 3/39，de_inferno R12”等证据行 | 这是明确的行动入口，下一步自然。                             |
| 进入具体分析   | 点击 R12 证据行                                              | 进入对应比赛的 Match Workspace，但落在泛化“概览”             | 没有带入 FalleN、R12 或“长枪局首死”这个问题。                |
| 找到并打开证据 | 手动切到回合、手动选 R12、打开 2D 回放                       | R12 中可看到 1:36 apEX 击杀 FalleN；2D 回放正确带入 R12、733 帧 | 回合 → 2D 回放的上下文连续。                                 |
| 回到原分析     | 从 2D 回放回“回合”                                           | 回合列表回到 R1                                              | 不仅丢失主页问题，连刚看的 R12 也丢失；回主页也只是回到泛化主页，不能回到原证据行。 |

[Actionability] 主页是当前最像“软件主动告诉我该看什么”的地方：它既给结论，也给可点击的证据。

[Evidence Flow] “现象”与比赛证据相连，但中间缺少原因层；`长枪局首死 3/39` 到 R12 后，用户只能自行重建“为何这是该问题的证据”。

[Context Continuity] 主页 → Workspace 丢失问题、选手、回合；R12 → 回放连续，但回放 → 回合又重置到 R1。这条闭环的断点是可复现的。

## 主任务 2：长期状态诊断

| 用户当前目标               | 自然尝试与实际结果                                           | 当前上下文                       | 下一步是否自然                                 |
| -------------------------- | ------------------------------------------------------------ | -------------------------------- | ---------------------------------------------- |
| “我最近状态不好，为什么？” | 我的主页直接呈现打法风格、个人趋势、本周该练什么、开局动线、最近比赛、道具价值 | 已有“这是我”的选手身份           | 主页本身是明确入口。                           |
| 追问某项长期问题           | 从主页离开后，左侧导航变为选手档案、开局动线、对枪复盘等分析能力 | 没有一个持续存在的“本次诊断”对象 | 用户必须理解每个页面分别能解释什么。           |
| 在档案中理解自己           | 选手档案给出画像、趋势、机制及指标快照                       | FalleN 的 4 场数据               | 是资料页，不会承接主页的某个诊断假设或证据链。 |

[Product Model] 产品有“近期状态入口”，没有一个持续的“长期诊断任务”。主页先替用户提出问题，离开主页后，诊断又退回为用户自己组织页面和指标。

[Information Architecture] 侧栏主要按分析能力组织，而不是按“继续诊断这个人”组织。

[Page Responsibility] 主页承担结论和练习建议；选手档案承担画像；开局与对枪承担专项分析。边界清楚，但三者没有组成一条诊断链。

## 主任务 3：理解一支队伍

自然入口是“赛事与队伍”，但落点是“排行榜”，不是 Team FURIA 的稳定对象页。

| 目标         | 实际操作与当前范围     | 得到的内容                                                   | 证据与连续性                                               |
| ------------ | ---------------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
| 选择 FURIA   | CohortScope 点选 FURIA | `聚合范围 7/7 场` 仍不变；排行榜改为 FURIA 阵容              | 选择表现得像筛选，实际是队伍透镜。                         |
| 看整体表现   | 赛事总览               | 全局 7 场总览、地图使用、攻防节奏，及 FURIA / Vitality 并列比较 | 有数据，但用户要自己从总览判断“FURIA 的特点”。             |
| 看经济与转化 | 转化与节奏             | FURIA 的 5v4 转化等数据                                      | 没有从总览带来的待验证假设或下一步。                       |
| 看对枪       | 对枪概览               | 首杀热点、按地图/时段的对枪事件，可进回放                    | 这是较清楚的证据入口。                                     |
| 看道具       | 道具价值               | HE、火、闪、烟等分项排名                                     | 数据页，与对枪/转化平行。                                  |
| 看控图       | 控图                   | 唯一明确解释“覆盖场基线为全局范围，队伍视图为该队贡献”的页面 | 概念正确，但只在此页说清，不能纠正前面已经形成的筛选预期。 |

[Information Architecture] 用户先选择了分析类型，再在其中观察 FURIA；不是围绕“FURIA”持续浏览整体、经济、对枪、道具、控图。

[Context Continuity] FURIA 透镜能跨上述分析页保留，但进入教练工作台后回到“全部队伍”，还需重新设定己方和对手。

[Information Hierarchy] 多个页面都有有效数据与局部解释，但没有统一的队伍画像来判断哪些发现是强项、问题，哪些只是某项指标。

## 主任务 4：对手备战

这条链实际走通了：

| 步骤         | 实际行为                            | 结果                                                         |
| ------------ | ----------------------------------- | ------------------------------------------------------------ |
| 进入备战     | 教练工作台 → `敌方侦察`             | 工作台有独立的己方/对手选择，不继承此前 FURIA 透镜。         |
| 设定对象     | 己方 Vitality、对手 FURIA           | 得到 FURIA 的开局事实簇与对局模式。                          |
| 查看代表证据 | 选中 `Team Vitality vs FURIA · R18` | 可见长枪局、人数站位、香蕉道/侧道分布、C4 目标、首杀率、证据回合；有“工作台 ↗”入口。 |
| 沉淀发现     | 点击 `加入`                         | `备战清单` 保留 de_inferno、R18、模式名称，并可 Markdown 导出。 |
| 形成报告     | 打开 `备战报告`                     | 自动生成以 FURIA 为对象的地图池、T/CT 模式与 Markdown 报告。 |

[Actionability] 教练工作台不是纯展示页；“模式 → 代表回合 → 加入清单 → 报告”真实可用。

[Context Continuity] 它是内部闭环容器，但不是全产品的工作流容器：经济、对枪、道具、控图页没有自然的“带着当前队伍与发现进入备战”路径。

[Page Responsibility] 教练页负责行动和沉淀，其他分析页负责观察；两者之间缺少交接。

## 专项实验 A：队伍透镜

| 用户预期                       | 实际行为                           | 页面变化                                                   |
| ------------------------------ | ---------------------------------- | ---------------------------------------------------------- |
| 选 FURIA 后只分析 FURIA 的比赛 | 范围仍显示 `聚合范围 7/7 场`       | 排行榜变为 FURIA 阵容；赛事总览仍使用 7 场总量与多队对比。 |
| 在每页都围绕 FURIA             | 转化、对枪、道具、控图页保留 FURIA | 各页显示 FURIA 的贡献或数据，但仍以全局比赛语料为分母。    |
| 带着 FURIA 去备战              | 进入教练工作台                     | 范围重置为全部队伍；必须重新选 Vitality / FURIA。          |

[Interaction Consistency] FURIA 与地图、赛事等 chip 外观相同，用户有充分理由把它理解为缩小语料的筛选器；实际语义却是“队伍透镜”。

[Product Model] “队伍透镜”只在控图页以“覆盖场基线 / 队伍贡献”说明，尚不是全产品一致、可感知的范围模型。

## 专项实验 B：赛事对象

| 入口                               | 实际代表的对象                                               |
| ---------------------------------- | ------------------------------------------------------------ |
| CohortScope 的“示例职业局（7 场）” | 分析范围中的赛事/集合筛选项。                                |
| 赛事与队伍 → 赛事总览              | 当前聚合范围的比赛、地图和队伍分析。                         |
| 赛事与队伍 → 赛事合集              | 明确写作 `Event → Stage → Series → Map` 的本地只读层级；“示例职业局”中含两场决赛、7 图。 |
| 管理 → 赛事                        | 赛事资源获取与生命周期：下载示例、导入 `<slug>.zip`、自动建立赛事→系列→地图并配对 demo；当前已导入赛事 1 个。 |
| 资料库                             | 本地 demo 的导入、列表、搜索和单场访问。                     |

[Product Model] “赛事”同时表示分析范围、赛事层级视图、导入集合、资源包和管理资产。每种含义都合理，但用户必须自行推断它们之间的生命周期关系。

[Discoverability] “赛事资产”位于管理之下，管理默认落在身份页；资料库空状态又将大型赛事引导到这里。入口多且职责不同。

## 仅使用允许分类的发现

- [Product Model] 个人诊断、队伍分析、赛事资产、备战清单各自有对象模型，尚未形成可在全产品传递的“当前人/队伍/赛事/问题/证据”状态。
- [Information Architecture] 主导航优先按分析能力分组；人、队伍、赛事等对象只能在若干页面内局部成立。
- [Context Continuity] 个人闭环在主页→比赛→回放→返回中连续丢失问题、选手和回合；队伍透镜也不会进入教练工作台。
- [Page Responsibility] 主页负责诊断提示，工作台负责沉淀，专项页负责数据；专项页与工作台之间没有交接责任。
- [Discoverability] “这是我”候选卡需要绕到档案页；赛事资产和赛事合集需要先理解多个入口的差异。
- [Information Hierarchy] 队伍和报告页有大量数据与模式，但缺少一个把“强项、问题、下一步证据”排序成画像的上层语境。
- [Evidence Flow] 对枪和回放有可用证据入口；主页问题卡能到比赛，但没有保留问题语义，原因链需要用户自行重建。
- [Actionability] 教练工作台可保存和导出；个人、队伍专项发现基本只能观看或另行导航。
- [Interaction Consistency] 同样的范围控件承载筛选与透镜两种不同含义，跨页保留规则也不一致。

## 四个问题

1. 当前最自然的组织单位是“分析能力”。主页和教练工作台局部按任务组织，但全局导航、队伍入口和专项页仍要求用户先选分析类型。
2. 最成熟的闭环是“已知对手备战”：敌方侦察 → 模式 → 代表回合 → 加入备战清单 → Markdown 报告。它已经具备行动与沉淀，只是尚未接住全产品其他页面的发现。
3. 最断裂的闭环是“个人问题 → 证据 → 回放 → 返回原问题”。主页发现问题很强，但一进入比赛就丢失来源，回放返回还会从 R12 重置到 R1。
4. 不能只靠改 UI 解决的，是四个产品结构决定：范围究竟是筛选还是透镜；人/队伍/赛事/问题/证据哪些状态应跨页面传递；个人诊断应是持续任务还是主页卡片加专项页；教练工作台是独立页面还是全局行动与沉淀容器。赛事的分析对象、层级集合与资产生命周期，也需要明确为可区分的产品对象。
